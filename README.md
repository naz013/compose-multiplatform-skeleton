# Compose Multiplatform Architecture Skeleton

A production-ready **Kotlin Multiplatform** project skeleton targeting **Android**, **iOS**, and **Desktop (JVM)**. It bundles pre-wired, independently usable modules so you can bootstrap a new KMP app without wiring the boilerplate yourself.

---

## 🗂 Project Structure

```
compose-multiplatform-arch/
├── androidApp/           # Android application entry point
├── composeApp/           # Shared Compose Multiplatform UI (Android · iOS · Desktop)
├── logging/              # Platform-aware logging abstraction
├── roomdatabase/         # Room KMP database with Repository pattern
├── sqldelightdatabase/   # SQLDelight KMP database with Repository pattern
├── datastore/            # DataStore Preferences (key-value persistence)
├── ktor/                 # Ktor HTTP client (networking + serialization)
├── datetime/             # kotlinx-datetime wrappers (date / time helpers)
└── localization/         # Runtime i18n / locale-switching engine
```

---

## 📦 Modules

### `composeApp` — Shared UI Layer
The heart of the app. Shared Compose Multiplatform screens and components that run on Android, iOS, and Desktop. Connects all other modules through a single `initKoin()` entry point.

- **Targets:** Android · iOS (arm64, x64, simulatorArm64) · Desktop (JVM)
- **Key tech:** Compose Multiplatform, Material 3, Lifecycle ViewModel, Koin DI
- **What to use it for:** Put your shared screens, navigation, and ViewModel here. Platform-specific UI code goes in `androidMain`, `iosMain`, `desktopMain`.

---

### `androidApp` — Android Application Shell
A thin Android `Application` + `Activity` that hosts `composeApp`. This is the deployable Android APK entry point.

- **Targets:** Android only
- **Key tech:** `androidx.activity:activity-compose`, Compose BOM, Material 3, Koin Android
- **What to use it for:** Android-specific setup (theme, splash, permissions, Koin init). Everything else belongs in `composeApp`.

---

### `logging` — Cross-Platform Logger
A lightweight `expect/actual` logging façade. Write `Logger.d(tag, msg)` once in common code; each platform routes it to the native logger (Logcat on Android, `println` on iOS/JVM).

- **Targets:** Android · iOS · JVM (Desktop)
- **Key tech:** Kotlin Multiplatform `expect/actual`
- **API:**
  ```kotlin
  Logger.d(tag, message)
  Logger.i(tag, message)
  Logger.w(tag, message)
  Logger.e(tag, message, throwable)
  Logger.v(tag, message)
  ```
- **What to use it for:** Drop-in replacement for platform loggers. No configuration needed.

---

### `roomdatabase` — Room KMP Database
A fully multiplatform Room database setup using `BundledSQLiteDriver` so it works on iOS and Desktop as well as Android. Ships with an example `Entity → DAO → Repository` pattern.

- **Targets:** Android · iOS · JVM (Desktop)
- **Key tech:** AndroidX Room 2.x, `androidx.sqlite:sqlite-bundled`, KSP, Koin
- **Structure:**
  ```
  ExampleEntity  (Room @Entity)
  ExampleDao     (@Dao — queries)
  ExampleRepository / ExampleRepositoryImpl
  MainDatabase   (RoomDatabase)
  ```
- **What to use it for:** Structured relational data that needs full SQL query power. Replace / extend `ExampleEntity` and add your own DAOs. Koin wiring is already in place.

---

### `sqldelightdatabase` — SQLDelight KMP Database
An alternative SQL database module using SQLDelight — write `.sq` files, get type-safe Kotlin APIs. Uses platform-specific drivers (Android, iOS Native, JVM SQLite).

- **Targets:** Android · iOS · JVM (Desktop)
- **Key tech:** SQLDelight 2.x, Koin
- **Structure:**
  ```
  DriverFactory (expect/actual per platform)
  DelightRepository / DelightRepositoryImpl
  Database       (generated by SQLDelight)
  ```
- **What to use it for:** Prefer SQLDelight when you want SQL as the source of truth (`.sq` schema files), multiplatform migrations, or need iOS without Room. Choose one of `roomdatabase` or `sqldelightdatabase` — or keep both for different data layers.

---

### `datastore` — Key-Value Preferences
Wraps `androidx.datastore:datastore-preferences` for KMP. Provides a `DataStoreFactory` with `expect/actual` file-path resolution per platform, plus an example `ExampleSettings` interface.

- **Targets:** Android · iOS · JVM (Desktop)
- **Key tech:** AndroidX DataStore 1.x, kotlinx-coroutines, Koin
- **Structure:**
  ```
  DataStoreFactory (expect/actual — resolves file path per platform)
  ExampleSettings / ExampleSettingsImpl
  LocalizationSettingsImpl (used by the localization module)
  ```
- **What to use it for:** Lightweight key-value storage (user preferences, feature flags, session tokens). Coroutine-based `Flow` API — no `SharedPreferences` boilerplate.

---

### `ktor` — HTTP Networking
A pre-configured `Ktor` HTTP client with JSON serialization, structured logging, and typed `Resources` routing. Ships with a working Open-Meteo weather API example.

- **Targets:** Android · iOS · JVM (Desktop)
- **Key tech:** Ktor 3.x (CIO engine), `ContentNegotiation`, `kotlinx.serialization`, Koin
- **Example:**
  ```kotlin
  // CurrentWeatherApi — typed REST call with Ktor Resources
  interface CurrentWeatherApi {
      suspend fun getCurrentWeather(request: CurrentWeatherRequest): CurrentWeatherResponse
  }
  ```
- **What to use it for:** Any REST/HTTP communication. Extend `ClientFactory` to point at your API host, add your own `@Resource`-annotated route objects and API interfaces.

---

### `datetime` — Date & Time Utilities
A thin wrapper module over `kotlinx-datetime` exposing common `LocalDate`, `LocalTime`, and `LocalDateTime` helpers for use in shared code.

- **Targets:** Android · iOS · JVM (Desktop)
- **Key tech:** `org.jetbrains.kotlinx:kotlinx-datetime`
- **What to use it for:** Any date/time logic in `commonMain` without touching platform APIs. Extend with your own formatting or calculation utilities.

---

### `localization` — Runtime i18n Engine
A full runtime localization system that goes beyond static string resources. Supports locale switching **at runtime** without restarting the app, driven by a `StateFlow`.

- **Targets:** Android · iOS · JVM (Desktop)
- **Key tech:** Compose `CompositionLocal`, `kotlinx.serialization`, `kotlinx-coroutines`, Koin
- **Core classes:**
  ```kotlin
  LocalizationManager  // holds currentLocale: StateFlow<AppLocale>
  StringKeys           // enum/sealed class of all translatable string keys
  StringResources      // JSON-backed string map per locale
  AppLocale            // value class wrapping a BCP-47 language tag
  LocalizationViewModel
  ```
- **Compose integration:**
  ```kotlin
  // Access strings anywhere in the Compose tree:
  val title = localizedString(StringKeys.AppTitle)
  ```
- **What to use it for:** Apps that need in-app language selection. Add new locales by dropping a JSON file and extending `StringKeys`.

## 🚀 Getting Started

1. **Clone** the repository.
2. Open in **Android Studio** (Hedgehog+) or **IntelliJ IDEA** with the KMP plugin.
3. Sync Gradle — all dependencies are declared in `gradle/libs.versions.toml`.
4. Pick your target:
   - **Android** → run `androidApp`
   - **Desktop** → run `composeApp:run` (or the `.run/` launch configs)
   - **iOS** → open `iosApp/iosApp.xcodeproj` in Xcode and run on a simulator

### Module dependency graph

```
androidApp
    └── composeApp
            ├── logging
            ├── roomdatabase  ──► logging
            ├── sqldelightdatabase ──► logging
            ├── datastore     ──► logging, localization
            ├── ktor
            ├── datetime
            └── localization  ──► logging
```

## 💡 How to Use This as a Template

| Goal | What to do |
|---|---|
| Add a new screen | Create a Composable in `composeApp/commonMain` |
| Add a REST endpoint | Add a `@Resource` + API interface in `ktor/commonMain` |
| Add a DB table | Add an `@Entity` + `@Dao` in `roomdatabase/commonMain`, register in `MainDatabase` |
| Add a SQL query file | Drop a `.sq` file under `sqldelightdatabase/src/commonMain/sqldelight` |
| Store a preference | Add a key to `ExampleSettings` in `datastore/commonMain` |
| Add a language | Add a JSON locale file + key in `StringKeys` inside `localization` |
| Add platform logging | Implement `Logger` in the appropriate `*Main` source set in `logging` |
